# MOEX Bot RUB factual snapshot network API v1

Status: repository delivery contract

Task ID: `rub_factual_snapshot_network_api_v1`

## Purpose

This service is a thin, read-only HTTP transport over the canonical persisted RUB factual snapshot.

Canonical flow:

```text
existing factual collection/runtime
-> MOEX_DATA_ROOT/state/rub_intelligence/chat_analysis_snapshot/current.json
-> governed chat snapshot consumer
-> read-only HTTP API
-> authorized external consumer
```

The API does not collect, refresh, generate, reinterpret, aggregate, forecast, recommend, trade, send Telegram messages, or mutate factual state.

## Canonical source and consumer

Canonical schema:

```text
rub_chat_analysis_snapshot.v1
```

Canonical persisted state relative to `MOEX_DATA_ROOT`:

```text
state/rub_intelligence/chat_analysis_snapshot/current.json
```

The network API calls only:

```python
src.moex_research.consumers.usdrubf_chat_snapshot_consumer.load_analysis_chat_snapshot
```

That governed consumer reads through the canonical `read_current_snapshot` reader and validates schema, project identity, read freshness, readiness, and the data-only authority boundary.

The existing producer remains separate. `moex-rub-chat-snapshot.timer` continues to refresh the snapshot every 10 minutes. This API has no timer and no refresh entrypoint.

## HTTP contract

The application binds only to loopback:

```text
127.0.0.1:8765
```

A non-loopback bind is rejected by the application. External TLS termination, reverse proxying, ingress, firewall policy, routable hostname, and network allow-listing are intentionally not selected by this repository task because the current repository does not define that infrastructure. Those are separate deployment/security decisions.

### `GET /v1/rub/factual-snapshot`

Authentication: required Bearer token.

Success: `200 application/json`.

The response body is the governed consumer result itself. The transport does not wrap, rename, aggregate, synthesize, or reinterpret factual fields.

Consequently, existing fields remain visible exactly under their canonical names, including:

- `schema_version`;
- `identity.generated_at_utc`;
- `readiness.status` and `readiness.component_statuses`;
- each component's own status, timestamps, provenance and quality fields;
- `read_freshness.read_at_utc`, `snapshot_age_seconds`, and `status`;
- `authority`.

A valid `PARTIAL`, `STALE`, `GOVERNED_BLOCKED`, retained, unavailable, or other governed component state is not hidden or upgraded by the API. A valid degraded snapshot is still retrievable with HTTP `200` so an authorized factual consumer can inspect the actual state.

The response includes `Cache-Control: no-store`.

### `GET /readyz`

Authentication: required Bearer token.

This is an operational readiness endpoint only. It does not provide alternative factual data.

It returns HTTP `200` only when both canonical conditions are true:

```text
readiness.status == READY
read_freshness.status == FRESH
```

Otherwise it returns HTTP `503` and reports the canonical readiness/freshness values. It also keeps snapshot generation time and governed read time distinct.

No additional application health endpoint is required.

### Other methods and paths

`POST`, `PUT`, `PATCH`, and `DELETE` return `405` and do not invoke the snapshot loader. Unknown paths return `404`.

## Timestamp semantics

Three time concepts must remain distinct:

1. `identity.generated_at_utc` — when the canonical persisted snapshot was generated by the separate producer.
2. `read_freshness.read_at_utc` — when the governed reader read the persisted snapshot for the current API request.
3. Source/component timestamps — timestamps already stored inside the canonical components.

The HTTP request/read time is never presented as source-data freshness and never replaces `identity.generated_at_utc` or source timestamps.

## Authentication and configuration

Required secret:

```text
MOEX_RUB_SNAPSHOT_API_TOKEN
```

No token value is committed to GitHub. `.env.example` contains only an empty placeholder.

At runtime the service resolves the token in this order:

1. direct process environment `MOEX_RUB_SNAPSHOT_API_TOKEN`;
2. the file named by `MOEX_ENV_FILE`, reading only `MOEX_RUB_SNAPSHOT_API_TOKEN` through `python-dotenv`.

The repository-governed service sets:

```text
MOEX_ENV_FILE=/home/trader/moex_bot/.env
```

Missing, blank, whitespace-corrupted, relative, symlinked, or non-file configuration fails closed before the HTTP server starts.

Requests use:

```text
Authorization: Bearer <token>
```

Comparison uses `hmac.compare_digest`. Invalid or missing credentials receive HTTP `401`; the snapshot loader is not called.

## Failure semantics

| Condition | Snapshot endpoint | Readiness endpoint |
| --- | --- | --- |
| Valid `READY` + `FRESH` snapshot | `200`, canonical payload | `200`, `READY` |
| Valid `PARTIAL` snapshot | `200`, canonical payload with state preserved | `503`, `NOT_READY` |
| Valid `STALE` snapshot | `200`, canonical payload with state preserved | `503`, `NOT_READY` |
| Missing persisted snapshot | `503 snapshot_unavailable` | `503 snapshot_unavailable` |
| Malformed/invalid snapshot | `503 snapshot_unavailable` | `503 snapshot_unavailable` |
| Missing/wrong Bearer token | `401 unauthorized` | `401 unauthorized` |

The HTTP layer does not fabricate fallback data and does not trigger refresh on any failure.

## Read-only authority boundary

The network service imports the governed consumer and standard-library HTTP/configuration code only. It contains no MOEX, CBR, news, oil, calendar, broker, Telegram, external-data, analysis, scenario, recommendation, B/S/OUT, or snapshot-refresh adapter.

The canonical authority fields remain authoritative. This task does not change Stage 3/4/5/7/9/10 semantics, FUTOI governance, trading-day governance, source selection, or the 10-minute snapshot producer cadence.

## Deployment boundary

Repository work alone does not authorize server apply.

After merge, a separate `server_apply` authority must:

1. verify the exact merged GitHub commit;
2. reconcile the canonical server repository with that commit;
3. ensure `MOEX_RUB_SNAPSHOT_API_TOKEN` exists in the governed parent project environment without printing or committing it;
4. deploy the repository unit using the project's authorized systemd installation procedure;
5. reload systemd and start/enable `moex-rub-factual-snapshot-api.service`;
6. verify that `moex-rub-chat-snapshot.timer` remains unchanged and active on its existing 10-minute cadence;
7. verify unauthenticated local GET returns `401`;
8. verify authenticated snapshot GET returns the canonical schema and preserved status/timestamp fields;
9. verify `/readyz` agrees with canonical `READY/FRESH` state;
10. verify service logs show no upstream refresh, broker, Telegram, or analytical action.

The current repository contains Source-of-Truth unit files but no canonical unit-install destination/script and no external ingress/TLS topology. Therefore this task does not invent either. Those deployment details must be resolved under the later server-apply/security authority before any external exposure.
